ScholarSync — IIL & Feedback System

Implementation guide for the Interaction Intelligence Layer and Rich Feedback System. This document explains what we're building, why, and how to make it work during the user testing phase.

What we're building

ScholarSync has a RAG platform with a knowledge base (NCERT, board syllabi, tenant material). Users chat with this KB and get grounded responses. Right now, every user gets the same quality of response regardless of who else has used the platform before them.

We're adding two systems that work together to make the platform continuously smarter from user interactions:

1
Rich Feedback System

Every chat response shows feedback options. Different users see different options based on their expertise level. A student sees "helpful / not helpful / confusing / incomplete." An SME sees all of those plus "expert validated / missing dimension / expert note." These signals tell us exactly what's working and what's not.

2
Interaction Intelligence Layer (IIL)

A three-part system that captures every interaction with rich metadata, curates the best ones into a supplementary knowledge layer, and uses expert patterns to proactively enrich responses for all users. When an SME deeply explores "Electromagnetic Induction" from five angles, those angles become available to every future student.

The key insight

An SME's 10-message deep-dive on Newton's Laws creates knowledge dimensions (misconceptions, cross-concept links, exam traps) that a student would never discover on their own. The IIL captures these dimensions and makes them available to every future student — automatically enriching their experience.

The three parts of the IIL

1
Part 1 — Rich interaction logging

The foundation. Every chat interaction is logged with structured metadata: who asked (and their expertise tier), what concept it maps to, how retrieval performed (which chunks, what scores), what the response looked like, and how follow-up questions chain together.

This captures 100% of interactions. Nothing is filtered or discarded at this stage.

Critical: must be live before any test user logs in

You cannot retroactively add metadata to past conversations. If an SME has a brilliant deep-dive in week one and your logging isn't ready, that data is permanently lost.

2
Part 2 — Derived knowledge curation

The flywheel. A scoring engine scans the interaction logs and flags high-value interactions as "curation candidates" — based on user tier, feedback signals, conversation depth, and novelty.

A human reviewer (platform admin) reviews each candidate, and if approved, the interaction is distilled into a clean "derived knowledge artifact" — a structured explanation tagged with the concept and dimension it covers.

These artifacts are embedded and indexed into a supplementary retrieval namespace (separate from the KB). When any user later asks about the same concept, retrieval blends KB content (70% weight) with derived knowledge (30% weight).

All curation is manually reviewed

No interaction enters the derived knowledge base without a human approving it. The scoring engine only flags candidates — it doesn't auto-approve.

3
Part 3 — Query pattern augmentation

The multiplier. Captures how experts decompose concepts — their questioning sequences, drill-down patterns, and multi-angle probes. These patterns are used to:

(a) Generate better starter prompts in focus cards — instead of "explain X", students see "what mistakes do students make with X?" because SME data shows that angle is valuable.

(b) Proactively enrich system prompts — when a student asks a simple question, the response naturally includes 1-2 additional dimensions (like a brief misconception flag) because expert data shows those dimensions matter.

Things to take care of

Logging must be live from day one

The entire IIL depends on rich interaction logs. If the logging schema isn't deployed before test users arrive, early interactions (often the most valuable SME sessions) are permanently lost. There is no way to retroactively add structured metadata to past conversations. This is the single biggest risk.

"Inaccurate" feedback is a hard reject

If any interaction receives an "inaccurate" signal from a teacher or SME, it must NEVER enter the derived knowledge base, regardless of how many positive signals it has. One factual error in the derived KB poisons every future response that retrieves it. The scoring formula assigns -10 (hard reject) to inaccurate signals.

Logging must not add latency to chat

The InteractionLog is created asynchronously after the response is delivered. If the logging pipeline fails, the user still gets their response — logging failures are captured in observability but never block the user experience. Never put log creation on the critical chat path.

Don't overload proactive enrichment

When a concept has rich derived knowledge, it's tempting to surface all of it. Don't. Cap proactive enrichment at 1-2 additional dimensions per response. More than that makes responses feel bloated and unfocused. Students came for a specific answer — enrichment should feel like a helpful bonus, not a lecture.

Off-syllabus content must not enter enrichment

If a derived artifact or interaction was flagged as "off-syllabus" by a teacher, it should NOT be used in proactive enrichment for students. The primary users are 11th and 12th class students — they need syllabus-aligned content, not college-level depth. The off-syllabus guardrail is specific to ScholarSync's educational context.

Blending weights are configurable, not hard-coded

The 70% KB / 30% derived split is a starting point. Store these as tenant-level configuration values, not code constants. During the test phase, you may need to adjust them based on whether derived content is helping or hurting response quality. Make it easy to change without a deployment.

User tier is server-side, not client-submitted

The expertise tier that determines which feedback options a user sees must be resolved server-side from the user profile. Never trust a client-submitted tier value. A student should not be able to submit "expert_validated" feedback by manipulating the request.

Where this plugs in to the existing platform

The IIL and Feedback System are additive layers. They plug into: (a) the existing Message entity (FK from InteractionLog and InteractionFeedback), (b) the existing RAG retrieval pipeline (new derived namespace added to retrieval), (c) the existing §8.3 system prompt pre-processing (enriched with derived knowledge and patterns), (d) the existing FR-DIR-3 starter prompt generation (enriched with exploration templates). No existing functionality is replaced or modified.

  • Create derived knowledge vector namespace
    Separate namespace in Pinecone (or equivalent) for derived artifacts. Tenant-scoped.
    P1
  • Create CurationCandidate entity and scoring engine
    Background job that scores interactions based on tier, feedback, chain depth, novelty. Threshold: score >= 5.
    P1
  • Create DerivedKnowledgeArtifact entity
    Schema per spec §4.5. Includes content, dimension tags, concept mapping, embedding reference.
    P1
  • Build LLM-assisted artifact extraction pipeline
    Takes a conversation chain, distills it into a clean standalone explanation. Versioned prompt template.

  • Build curation review admin UI
    Candidate list (filterable by status, concept, score). Detail view with full interaction chain and feedback. Approve/reject with notes.

  • Extend retrieval pipeline with derived namespace and blending
    Three-way retrieval: KB (70%) + user sources (contextual) + derived (30%). Weights stored in tenant config.

  • Build concept coverage map admin view
    Matrix: concept (rows) x dimension (columns). Cell shows artifact count. Gaps highlighted.

    Extract questioning patterns from SME chains (depth >= 3). Store dimension sequence and template prompts.

    Extend FR-DIR-3 to use template prompts as seeds. Personalized with student interest profile.

  • Build proactive response enrichment in system prompt pre-processing

  • Build monitoring dashboard for IIL metrics
    Logs/day, feedback rate, candidate pipeline, coverage fill, derived hit rate, inaccuracy alerts.
    P2

Enforcement checks (verify before go-live)

  • Tier enforcement: student cannot submit expert_validated
    API returns 403 if user tier is insufficient for the signal type.
  • Inaccurate requires free_text
    API returns 400 if signal_type = inaccurate and free_text is empty.
  • Tenant isolation on derived namespace
    Derived artifacts from tenant A are never retrievable by tenant B.
  • Concept scoping on derived retrieval
    Derived artifacts for concept X don't appear in retrieval for concept Y.
  • Logging pipeline failure doesn't block chat
    Simulate logging failure — user still gets their chat response. Failure shows in observability logs.
  • Blending weights are configurable without deployment
    Change KB/derived weights via admin config — takes effect on next request, no restart needed.
  • Off-syllabus artifacts excluded from enrichment
    If an artifact's source interaction has off_syllabus feedback, it's excluded from proactive enrichment.
  • User_tier is server-resolved, not client-submitted
    API ignores any tier value in the request body. Always resolves from user profile server-side.
